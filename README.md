## 版本状态：v0.5 - 数据加工厂与 HEX 双向解析 (阶段 1 上半场)

### v0.5 核心功能
1. **重构数据加工层**：抽离 `FormatData` 函数，作为所有发送逻辑的唯一入口，实现数据格式的统一处理。
2. **工业级 HEX 解析器**：摒弃官方 `QByteArray::fromHex` 的静默失败行为，手写 `ParseHexData`。实现严格的白名单过滤（0-9, A-F, a-f），对 `G~Z` 等非法字符直接拦截并报警，坚决不让脏数据流向硬件。
3. **位运算底层拼装**：利用 `(highVal << 4) | lowVal` 将两个 4-bit 的数值精准拼装成一个 8-bit 字节（`unsigned char`）。
4. **数据帧补全**：根据 UI 勾选状态（如“发送新行”），自动在数据流尾部追加 `\r\n`。

---

## 📐 架构重构 (数据加工厂的诞生)

在引入 HEX 转换和换行处理后，原有的单一发送逻辑变得臃肿。因此引入分层设计：
*   **触发层 (Trigger)**：按钮点击、定时器触发。
*   **加工层 (Processor)**：`FormatData` 接收原始文本 -> 判断是否走 HEX 解析 -> 判断是否加换行 -> 输出标准 `QByteArray`。
*   **执行层 (Execute)**：底层 `QSerialPort::write()` 将加工好的字节流甩入系统缓冲区。

## 🎯 开发过程中的踩坑记录（v0.5 阶段）

1. **致命逻辑缺陷：官方库的“静默截断”**
   - **现象**：使用 `QByteArray::fromHex("A1 G2")`，程序不报错，但发出去的字节流错乱或丢失。
   - **原因**：官方 API 遇到非法十六进制字符会直接忽略，导致数据长度错位，这对工业设备是致命的。
   - **修复**：手写 `ParseHexData` 函数，增加预处理（去空格）和严格校验（偶数长度、字符白名单）。遇到非法字符立刻 `return QByteArray()` 并弹窗，拒绝发送任何残缺数据。

2. **字符串拼写错误：换行符变成了普通字符**
   - **现象**：勾选“发送新行”后，下位机收到的是一堆乱码。
   - **原因**：在 `append()` 时，错将 `"\r\n"` 写成了 `"/r/n"`。反斜杠写成了正斜杠，导致发出去的是 4 个普通字符，而不是回车换行。
   - **修复**：严格区分转义字符，改为 `processedData.append("\r\n");`。

3. **流程短路：只处理了 HEX，漏了普通文本**
   - **现象**：不勾选 HEX 发送时，程序发送空包。
   - **原因**：`FormatData` 中 `if(checkbox->isChecked())` 只处理了勾选的情况，没有写 `else` 分支去处理普通文本。
   - **修复**：补全 `else { processedData = rawText.toUtf8(); }`，确保无论是否勾选，数据都能正确流转。

4. **报错后继续“投毒”**
   - **现象**：HEX 解析失败弹窗提示后，程序依然发出了空数据。
   - **原因**：弹窗后没有 `return` 中断函数，程序继续往下执行了 `write()`。
   - **修复**：在 `if(!ok)` 弹窗后，无条件加一句 `return QByteArray();`，切断执行链路。

## 🤔 开发过程中的疑惑与解答

### 疑惑 1：为什么 HEX 转换不能用现成的 `fromHex`，非要自己用位运算写？
- **解答**：工业软件的第一原则是“数据完整性”与“可控性”。`fromHex` 面对非法字符（如用户手滑输入的 `G`）会静默失败或截断，导致下位机收到半截指令而死锁。自己手写解析逻辑，能清晰地把控“字符校验 -> 提取数值 -> 左移拼装”的每一个环节，实现“要么全发对，要么彻底不发并报警”。

### 疑惑 2：为什么十六进制只能有 0-9 和 A-F？
- **解答**：这是数学的本质。十六进制是逢十六进一，一位（digit）必须能表示 0-15 共 16 个数。人类数字只有 0-9，因此借用了 A-F 代表 10-15。如果出现 G（16），则该位溢出，必然发生位错乱。因此 G-Z 在 HEX 语法中属于绝对的“外星语言”，必须拦截。

### 疑惑 3：为什么在进行 HEX 转换时，要求输入去掉空格后的字符长度必须是偶数？
- **解答**：这涉及计算机底层的字节（Byte）与比特（Bit）的物理关系。
    1. 计算机传输和存储的最小单位是 1 个字节（Byte），即 8 个比特（Bit）。
    2. 在十六进制中，**1 个字符（0-9, A-F）仅代表 4 个比特（半字节，Nibble）**。
    3. 必须用两个十六进制字符，才能拼成一个完整的字节。例如 `A` (`1010`) 和 `1` (`0001`)，拼成 `0xA1` (`10100001`)。
    4. 如果字符长度为奇数（如 `"A1 B"` 去空格后长度为 3），在循环取数时会导致**数组越界**，或者只能拼出半截残缺字节，导致向硬件发送的指令发生错位。
    5. **工程防线**：在工业级通信中，残缺数据会导致下位机解析器直接崩溃或死锁。因此必须在入口处拦截奇数长度的输入，直接报错，绝对不发送任何残缺或半截的指令。

## 💡 个人核心收获

1. **防御性编程的底线**：任何接收外部输入（用户输入、硬件串口读入）的接口，都必须假定输入是充满恶意的、错误的。必须在入口处做严苛的校验（白名单机制），死守边界条件。
2. **位运算是底层通信的通用语言**：通过 `(高4位 << 4) | 低4位` 完成字节拼装，这是 CPU 处理数据最原始、最高效的方式。
3. **逻辑与执行分离**：`FormatData` 加工厂的建立，使得后续无论加入“定时发送”还是“多文本循环”，只需关注“何时触发”，而不用再操心“数据如何转换”，极大降低了并发调度的复杂度。
